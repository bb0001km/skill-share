## channel_comment + SQLite .db — ПОСТРОЕНО (17.10.26)

Модуль «Комментарии в канале» доведён под эталон (движок+UI): массовый режим
`message_actions --comment-mode account|list`, `discover_comment_channels`/
`pick_channel_posts`/`comment_on_channels`, пул аккаунтов (как edit), повторные
проходы (`--launch-count`), skip_answered с реальной проверкой `_already_answered`.
UI — редактор+пресеты-dropdown+dropdowns режима/поста+панель КАНАЛЫ (list) с
«Открыть» из БД. Пресеты переписаны в эталонный dropdown (_presets_bar: Export/
Import файлом на серверных роутах). Наборы каналов — таблица `channel_sets`.

**SQLite .db как переносимый формат данных (решение Фёдора 17.10.26):** Postgres
ОСТАЁТСЯ рабочим хранилищем фермы (аккаунты/lease/флуд/параллельный парсинг —
SQLite там плох из-за блокировки на запись). Данные-артефакты (собранные юзеры)
выгружаются/загружаются в переносимый `.db` через ядро `sqlite_io.py`
(write_rows/read_rows/list_tables/count_rows, читает и чужие .db из DB Browser/
SQLiteStudio/Expert). collector: `--out *.db` + чтение .db в merge/exclude
(диспетчер `rows_to_file`/`file_to_rows` по расширению). Веб: `/api/collected/
export.db` + `/import`. НЕ сносить Postgres на SQLite целиком — это был явный
выбор владельца (Вариант 1).

**ГРАБЛЯ `collector._save_rows` (баг, залогирован save_rows_silent_swallow):**
пишет через ИМЕНОВАННЫЕ psycopg2-параметры по ВСЕМ колонкам → отсутствующий
ключ ИЛИ явный NULL в NOT NULL-колонку (`collected_at`/`has_photo`/`priority`/
`status`/`source_chat`) роняет execute, а `except: pass` его ГЛОТАЕТ, и отчёт
врёт «N upsert» (считает ВХОД, не реальные записи). Любой, кто шлёт неполные
строки в _save_rows (импорт .db), молча теряет их. Заполнять ВСЕ обязательные
колонки перед вызовом.

ПОЧИНЕНО (коммит 8c4e350). МЕХАНИЗМ, который делал баг хуже «одной потерянной
строки»: в ОДНОЙ psycopg2-транзакции первый же упавший execute АБОРТИТ всю
транзакцию — дальше каждый execute падает `InFailedSqlTransaction`, а итоговый
commit на аборченной транзакции делает ROLLBACK → терялся ВЕСЬ набор, не только
битая строка. ФИКС (общее правило для любого цикла INSERT в одной транзакции):
оборачивать КАЖДУЮ строку в `SAVEPOINT sp_row` → INSERT → `RELEASE SAVEPOINT`;
в except — `ROLLBACK TO SAVEPOINT sp_row`, считать `failed`+`first_err` и
логировать («⚠ не записано N из M, пример …»), НИКОГДА не `except: pass`. Тогда
битая строка откатывается точечно, валидные коммитятся (проверено на реальной БД).
Отчёт дополнять числом сбоев; `saved`/`failed` — РЕАЛЬНЫЕ, не вход.
ГРАБЛЯ мока при этой правке: ручной `Cur.execute(self, q, p=None)` в сторожах,
делающий `p['user_id']` на КАЖДОМ вызове, падает на paramless `SAVEPOINT`/`RELEASE`
→ грепнуть мок-курсоры и защитить `if p:` перед разбором параметров.

SQLite .db — выгрузка/загрузка есть и для НАБОРОВ КАНАЛОВ (`/api/channel-sets/
{name}/export.db` + `/import`, кнопки ⬇.db/⬆.db в панели комментариев) и для
собранных юзеров (страница `/module/collected_db`, пункт меню «База собранных»).
Импорт чужого .db — через `_extract_channels`/аналог: читать ЛЮБУЮ схему
(колонки channel/link/username/… или первое непустое значение строки), не
завязываться на имена колонок DB Browser/SQLiteStudio/Expert.

**ЖИВОЙ ПРОГРЕСС фонового прогона** (Фёдор просит «сколько осталось», не

эту строку в ответах «статус», пока тесты крутятся.

**Плагина `pytest-timeout` в проекте НЕТ.** Флаг `--timeout=300` даёт
`error: unrecognized arguments`, и прогон не стартует вовсе. Один раз
это выглядело как успех: код возврата был 0, потому что он приходит от
`tail` в конце конвейера, а не от pytest. Читать сам вывод, а не код.

**Работая ПО ОДНОМУ МОДУЛЮ, полный прогон НЕ нужен каждый раз.** Гонять
прицельные тесты модуля (`pytest tests/test_<модуль>*.py -q`) — это
СЕКУНДЫ. Полный прогон всей фермы звать ОДИН раз, на финальной приёмке
модуля, и только `background=true, notify=true` (не ждать 9 минут).

**Параллель `-n 4` (pytest-xdist, 4 ядра) даёт ~2.6x (9:27 → ~3:37), НО
полную ферму ломает ложными падениями:** ~24 теста работают с ЖИВОЙ
папкой `accounts/` (пишут пробу в реальную папку, напр.
`test_session_reseat_guard` кладёт `gap_probe.session`; аудит-сторожа
типа `test_money_vault_balance_audit` снимают снимок до/после). При `-n`
эти тесты уезжают в РАЗНЫЕ воркеры: один кладёт пробу, teardown-сторож
соседнего процесса ловит этот миг и краснеет «ТЕСТ ТРОНУЛ БОЕВОЕ» —
ложно, живые данные целы (проверить: тот же файл ПОСЛЕДОВАТЕЛЬНО зелёный,
`sync_audit.py` показывает прежние числа). Безопасная полная параллель
требует серийной изоляции этих ~24 (один воркер через `xdist_group` +
`--dist loadgroup`) — простой conftest-хук по признаку это НЕ закрыл
(тесты шарят один путь глубже), не стоит возни. Использовать `-n` только
на подмножествах, НЕ трогающих `accounts/`.

**Расширил список колонок в SELECT — сначала грепни тесты на этот запрос.**
Ручные `FakeCur`-моки возвращают кортеж СТАРОЙ арности, и распаковка
`a, b, c, d, e, f = row` падает `ValueError: not enough values to unpack` на шарде,
который ты не прогонял. Делать распаковку ТЕРПИМОЙ к арности:
`a,b,c,d,e = row[:5]; f = row[5] if len(row) > 5 else None` — прод-БД отдаёт
новую колонку, моки старую арность, оба работают.
ТО ЖЕ при РАСШИРЕНИИ интерфейса общего объекта в движке (новый вызов
`client.is_connected()` и т.п.): хэндролл мок-клиенты реализуют СТАРУЮ форму
и падают `AttributeError` на шарде, который ты не прогонял. Новый вызов на
общем объекте — через `getattr(obj, "meth", default)` ЛИБО грепнуть мок-классы
в тестах и дописать метод. Любое расширение формы (колонки ИЛИ методы) ломает
ручные моки — проверять до коммита.

**Тест-файл НЕ подменяет `sys.modules` на уровне модуля.** `sys.modules["x"] = mock`
в теле тест-файла выполняется при ИМПОРТЕ (pytest собирает файл) и глобально
ломает другой тест (`ImportError: cannot import name ... from "x"`). Ставить моки
внутри функции-прогона с восстановлением в `finally` (save/restore prev), не на топе.

**Проверять «не моя ли это регрессия» — АНАЛИЗОМ, не `git stash`.** Понять, падал ли
тест до правок: смотри, читает ли тест ТВОИ изменённые файлы (напр. UI-label-тесты
`test_seven_modules_parity`/`test_accounts_panel_etalon_labels` читают `web/app.py`
KIND_LABELS — не трогал app.py → это существующий пробел UI-паритета, не твоя
регрессия). НЕ через stash: `git stash push -- <пути>` АБОРТИТСЯ, если среди путей
есть untracked-файл (новые `ops_*.py`/`mass_ops.py` в репо untracked) — стеш не
создаётся, и «проверочный» прогон идёт С твоими правками (вывод обманчив). Хуже —
голый `git stash pop` достаёт ЧУЖОЙ ранее сохранённый стеш (в репо висит
`t3-review-fix-wip`), заливая конфликты в файлы, которые ты не трогал. Если уж
залил — откат по файлу: `git checkout --ours -- <file>` (берёт сторону ДО pop),
стеш в `stash list` остаётся цел; а для реально чистого прогона без правок —
отдельный `git worktree`, не stash.

## Массовые действия исполнять ЧЕРЕЗ warm_scheduler/warm_routes, НЕ залпом

Планировщик случайных маршрутов УЖЕ построен — не писать второй:
`warm_scheduler.py` генерит на КАЖДЫЙ аккаунт уникальный случайный маршрут
(`random.choice(ACTIONS)`, кумулятивные задержки, случайный порядок),
сохраняет в таблицу `warm_routes` (`session_id, step_index, action_type,
delay_min, status, executed_at`), а `--tick` исполняет готовые по времени
шаги (`_execute_step`) и отмечает `done`; дневной бюджет — `warm_daily_budget`,
когорты/рандомизация стадий — `warm_orchestrator.py`.

Один заход, меняющий разом фото+имя+username+bio = заметный паттерн фермы;
те же правки, размазанные по часам среди обычной активности = как живой
человек. (Форум Expert просит именно такой планировщик, у них его НЕТ —
наше преимущество; БЗ source=telegram.)

**ПОСТРОЕНО — не писать заново, пользоваться:**
- `warm_scheduler.enqueue_profile_changes(conn, session_ids, fields, spread_days=2)`
  ставит профильные шаги в `warm_routes`: ОДНО поле за шаг, случайный порядок,
  кумулятивные задержки с де-корреляцией (сдвиг окна ±40 мин ДЕТЕРМИНИРОВАННО из
  `session_id`), ≤2 поля/день. Значения по ГЕО+ПОЛУ (`accounts.gender` +
  `generate_name(gender,locale)`, locale из страны; username из того же имени;
  bio под пол; фото — лицо по полу из пула), уникальность имён по ферме. ПРОПУСК:
  frozen/banned/broken, трастовые (`TRUST_SIDS`), апелляция, свежие <3д (только
  имя/username — карантин), вход <1ч. CLI: `--enqueue-profile SID1,SID2
  --fields photo,name,username,bio --spread-days 2`. Только ПЛАНИРУЕТ, в Telegram не ходит.
- Типы шагов `set_photo/set_name/set_username/set_bio/set_privacy` в
  `PROFILE_ACTIONS`, маппинг в действия apply — `PROFILE_MAP`. В случайную
  генерацию маршрута (`plan_for_account`) НЕ входят — только через enqueue.
- `_execute_step` для профильного типа делегирует в
  `apply_actions.apply_one_field(sid, mapped, value)` (= `apply_sequence` на ОДНО
  поле: прокси fail-closed + замок + паузы из профиля + сверка get_me + запись
  подтверждённого значения в БД + заморозка→БД). `cmd_tick` подхватывает и
  аккаунты НЕ в прогреве, если у них есть pending-профильные шаги; профильные шаги
  НЕ тратят дневной бюджет прогрева (`mark_done` без sid); `apply_one_field`
  вернул `'frozen'` → снять шаг и не долбить дальше.
- Значение шага хранится в колонке `warm_routes.value`
  `ALTER TABLE ... ADD COLUMN IF NOT EXISTS value TEXT`). `get_me`-подтверждение
  ДО записи в БД (иначе в базе окажется значение, которого в профиле нет —
  рассинхрон БД↔профиль).
- МИНИАТЮРЫ АВАТАРОК для панели (решено 14.10): при успешной простановке фото
  `apply_sequence` делает превью 96px ИЗ ЛОКАЛЬНОГО лица (того, что ставим) →
  `avatars/thumbs/<sid>.jpg`, путь в `accounts.avatar_thumb` (колонка добавлена
  `ALTER TABLE accounts ADD COLUMN IF NOT EXISTS avatar_thumb TEXT`). БЕЗ трафика —
  не скачивать текущие аватарки у аккаунтов через прокси (жжёт гигабайты; Фёдор
  выбрал «только по мере простановки»). NULL → серый плейсхолдер. Отображение —
  на НОВЫЙ интерфейс (эталон Expert: таблица # | Avatar(кружок 40px) | Phone=session_id,
  серый силуэт когда фото нет).  Данные готовы: `SELECT session_id, avatar_thumb,
  first_name, last_name`.
- УЛУЧШЕНИЯ ЗНАЧЕНИЙ (14.10): (1) **bio** в enqueue — через готовый
  `mass_actions.generate_bio_llm(account_row, conn)` (наш LLM-роутер, fallback на

смены поля) — скилл `telegram-account-warming`, `references/identity-and-proxy-rules.md`.

**Прогон/демо профильного шага ВЖИВУЮ, не задевая всю ферму:** `--tick` заходит во
ВСЕ warming-аккаунты + все с pending-профильными шагами. Чтобы применить/показать на
КОНКРЕТНЫХ аккаунтах — цикл по их sid напрямую: `next_step(conn,sid)` →
`_execute_step(sid, action, value)` → `mark_done(conn,id,"")`/`mark_failed`, а НЕ полный
`--tick` (иначе логинишься во всю ферму). `next_step` отдаёт СЛУЧАЙНЫЙ из готовых шагов,
поэтому чтобы гарантированно выполнился нужный ПРОФИЛЬНЫЙ шаг (а не прогревный), временно
`UPDATE warm_routes SET delay_min=0` на целевом и `+100000` на конкурентах того же
аккаунта; один заход = один логин (соблюдает ≥1ч между входами). Запускать через
`systemd-run --slice=system.slice`. После демо вернуть оставшимся шагам нормальные
разнесённые задержки (иначе штатный cron-`--tick` применит их <1ч после демо-входа).

**Ручной живой прогон НЕ изолирован от cron.** warm/orchestrator/trust `--tick`
крутятся в cron каждые 5-10 мин и сами заходят в аккаунты — твой ручной вход
легко ляжет <60 мин после их. Страж «пересаживание <60 мин» ТОЛЬКО ПРЕДУПРЕЖДАЕТ,
НЕ блокирует (вход всё равно состоится); одновременную коллизию ловит lease-замок
(второй процесс → «сессия занята — пропуск»). Для чистого демо брать аккаунт, в
который сегодня НЕ заходили (`updated_at` вчерашний), либо принять риск осознанно —
warn за отказ НЕ считать.

**Read-only скрипт на общем psycopg2-conn → `conn.autocommit = True`.** Иначе
проглоченная ошибка SELECT (напр. `build_bio_context` ловит сбой запроса в
`except: pass` без rollback) оставляет транзакцию аборченной, и СЛЕДУЮЩИЙ запрос
падает `InFailedSqlTransaction: current transaction is aborted`. autocommit на
чтениях это снимает (apply_one_field открывает свой conn — не делит с ним).

## Паузы между действиями — ОДНА модель + профиль аккаунта, без LLM-на-паузу

«Каждый раз разные» паузы УЖЕ есть: `behavior.human_delay` — логнормаль
(тяжёлый хвост), random на каждый вызов. «Индивидуально на аккаунт» тоже
есть: профиль-темперамент в `accounts.behavior` (хронотип, активные часы,
read_delay_min/max, think_min/max), генерится один раз. Темп паузы брать из
профиля через `behavior.action_pause(profile, scale=1.0)` (медиана=√(lo·hi)
из read_delay_min/max, `scale>1` для долгих — выбор фото); воркер грузит
`get_profile(sid, conn)` и прокидывает `params["_profile"]` в операции.
НЕ добавлять второй генератор пауз и НЕ звать LLM на каждую паузу: своя
модель рядом = ВТОРАЯ расходящаяся модель поведения → прогрев и действия
выглядят как разные люди на одной сессии (палево), плюс LLM не держит
правильное распределение с хвостом. LLM максимум — ОДИН раз при заводе,
чтобы задать профиль.

**UI-ДЕФОЛТ (решено 15.10.26, приказ Фёдора):** человеческая модель пауз —
ДЕФОЛТ без всякого выбора. Поля формы «Задержка между действиями MIN/MAX»
(и потоковые delay_min/max) ПУСТЫЕ/0 → движок сам ставит паузы по профилю
аккаунта (`apply_sequence` всегда зовёт `action_pause(profile)`). Это уже так
на уровне движка — доп. тумблера «Случайно/по-человечески» НЕ добавлять (лишняя
работа, Фёдор против). Поля в форме НЕ удалять: остаются как ОПЦИОНАЛЬНЫЙ ручной
темп на случай, когда нужен свой фиксированный. В mass_actions.html над полями —
акцентная плашка `.ma-pace-note`, объясняющая это (пусто = авто-модель).
По ТГ-ограничению: автоудаление сообщений Telegram даёт только фикс. периоды
(выкл/1 день/1 неделя/1 месяц), минут/часов НЕТ (посекундно только секретные чаты) —
поле «TTL в минутах» не делать, сервер отвергнет.

## account_probe.locked_client — проверять путь к сессии через account_store

`account_probe.locked_client` (строка ~376) исторически строил путь как
`ACCOUNTS_DIR/<sid>.session` — хардкод папки `accounts/`. Аккаунты в
`accounts_spamblock/`, `accounts_frozen/` и других категориях при этом
давали «сессия под замком — пропуск» (файл не найден → `acquire_session_lock`
возвращает `False`). Симптом неочевидный: замок как будто взят, хотя его нет.

**Правило:** в любом новом хелпере, принимающем `sid` и открывающем сессию,
путь строить ТОЛЬКО через `account_store.locate(sid, Path(BASE_DIR))`; если
`None` — fallback на `accounts/<sid>.session`. Хардкод `accounts/` — дефект.

```python
import account_store
from pathlib import Path

sid = str(acc["session"])
folder = account_store.locate(sid, Path(BASE_DIR))
if folder:
    session_path = os.path.join(BASE_DIR, folder, sid + ".session")
else:
    session_path = os.path.join(ACCOUNTS_DIR, sid + ".session")
```

**Это касается и третьесторонних хелперов в любом файле проекта** — перед
добавлением новой функции, принимающей `sid`, грепнуть `ACCOUNTS_DIR` вокруг
пути-формирования и заменить на `account_store.locate`.

## Фоновые пайплайны на сервере — три обязательных правила

1. **`/usr/bin/python3.10` для router-скриптов в bash**, не `python3`.
   Hermes-python не имеет `pg8000`, поэтому `ask_claude.py` падает на
   `import log_db` ещё до вызова модели. Проверка: `python3.10 -c "import log_db"`.

2. **Не редактировать `.sh`-скрипт пока он выполняется** — bash читает файл
   построчно на ходу. Правка запущенного скрипта приводит к непредсказуемому
   поведению. Вместо этого — отдельный скрипт-сторож (watcher), который ждёт
   артефакт и только потом обрабатывает.

3. **Вторичную обработку (индексация в БЗ) делать отдельным сторожем**, а не
   в теле основного скрипта. Сторож ждёт, пока файл перестанет расти
   (`sleep 30; проверить wc -c`), потом запускает индексацию. Это развязывает
   генерацию и постобработку и переживает прерывание основного процесса.
   Образец: `/root/tao_ref/kb_index_watch.sh`.

### Прямой LLM-эндпоинт: контракт `llm_registry.get_endpoint()` — `{url, key, model}`

Движки, что ходят в GPT НАПРЯМУЮ через настроенный эндпоинт (не через каскад
router.py) — chat_responder, commenter, умный автоответчик `answering_machine_smart`
— берут конфиг из `llm_registry.get_endpoint(name)`. Функция возвращает
`{"url": ..., "key": <УЖЕ РАСШИФРОВАН>, "model": ...}`. ГРАБЛЯ: потребитель,
читающий `endpoint.get("api_key")`/`endpoint["endpoint_url"]` (имена КОЛОНОК БД,
не ключи словаря) получает None → ложное «у эндпоинта нет ключа», хотя ключ
прописан и валиден. Плюс повторный `decrypt_key()` над уже расшифрованным ключом
ломает его. ПРАВИЛО: читать `endpoint["key"]`/`endpoint["url"]`/`endpoint["model"]`,
ключ НЕ расшифровывать второй раз. Эталон-потребители (`llm_gen`, `commenter`,
тест настроек в app.py) уже так делают — при новом LLM-движке копировать их
чтение, не изобретать имена полей. Проверка ключа — живым запросом
(`generate_reply(name, "короткий промпт")`), мок не ловит рассинхрон имён.

ДЕФОЛТНЫЙ эндпоинт МОЖЕТ БЫТЬ МЁРТВ. `llm_gen.list_available()` отдаёт
эндпоинты в порядке добавления; у ПЕРВОГО ключ бывает протухшим, а рабочий —
глубже (у Фёдора живой только часть из deepseek/openrouter/«Open AI»).
Потребитель, берущий `list_available()[0]` как дефолт, падает с LlmGenError,
хотя рабочий эндпоинт в списке есть. ПРАВИЛО: когда эндпоинт не выбран явно —
ПЕРЕБИРАТЬ кандидатов (явный + все из list_available) и брать ПЕРВЫЙ, что
реально ответил непустым (`_chat_complete` в try, ошибка → следующий), а не
слепо `[0]`. Это касается и персона-генератора, и дефолта автоответчика.
Протухший ключ — НЕ durable-факт (Фёдор обновит), durable — именно перебор.

### LLM-генерация в движках модулей (bio/username/имена)

Звать наш роутер /root/router/router.py через subprocess, не import
(изоляция окружения): `subprocess.run([sys.executable,
"/root/router/router.py", prompt], ...)`. Роутер печатает ответ ПОСЛЕ
маркера `--- РЕЗУЛЬТАТ ---` (router.py:82,416) — парсить
`out.split("--- РЕЗУЛЬТАТ ---",1)[1].strip()`, fallback — последний
непустой абзац. Функцию генерации делать с параметром llm_call=None
(по умолчанию реальный роутер) — тест подсовывает мок, БЕЗ реального
LLM/БД. Любая ошибка LLM/БД — fallback на алгоритмическую генерацию
(randomize_bio/транслит имени), не исключение наружу.

**ГРАБЛИ ПАРСИНГА РОУТЕРА (живьём 15.10.26, поймал live-тест на реальном аккаунте):**
(1) Вывод роутера насыщен ДЕКОРАТИВНЫМИ разделителями (===/---). Наивный
`out.split("--- РЕЗУЛЬТАТ ---")[1].strip()` или fallback `lines[-1]` может вернуть
строку «====…» вместо текста — и она ушла в bio живого аккаунта. Парсить через
`mass_actions._extract_router_result`: первая содержательная строка после маркера,
ПРОПУСКАЯ строки без единой буквы/цифры (`any(ch.isalnum())`). timeout роутера —
≥150с (каскад бывает дольше 60с, иначе обрыв→пусто→fallback). В generate_bio_llm —
guard: bio без alnum → fallback (не писать мусор).
(2) ГЕО/ПИСЬМЕННОСТЬ имени: в промпт `generate_name_llm` нельзя слать 2-буквенный
КОД страны — LLM путает «CO» с Colorado и выдаёт англо-имя на колумбийский аккаунт
(палево, антидетект!). Разворачивать код в полное название (`_COUNTRY_RU`) И задавать
письменность: латиноам./зап. — латиницей, RU/UA/KZ — кириллицей (иначе «Андрес
Эскобар» кириллицей на +57). Сторож — test_llm_identity (extract/bio-guard/geo-script).
ВЫВОД: LLM-путь имён ХРУПЧЕ алгоритмического name_library по гео+письменности —
приёмку LLM-полей делать ТОЛЬКО живым прогоном (мок зелёный ≠ корректно вживую). ПРИЁМКА:
тесты с моком зелёные НЕ доказывают реальный путь — проверить
живым вызовом на одном аккаунте (маркер роутера реально печатается,
результат парсится). История для контекста ЕСТЬ НЕ на все 66
аккаунтов (trust_personas ~11, warm_dialogue_log ~58) — всегда fallback
на accounts (имя/пол/страна/язык). Фото: pic_library (318) + pic_usage
(учёт, уникальность на профиль); имена: name_library (302). Полное
ТЗ доработки полей массовых действий — `SPEC_mass_actions_llm.md` (4 среза:
bio✓ → фото → username → имена).

## После каждого доработанного модуля — ПЕРЕЗАПУСТИТЬ сервис (приказ Фёдора)

Веб-панель поднята без `--reload`: правки в `web/app.py`/шаблонах НЕ
видны, пока сервис не перезапущен. Фёдор смотрел старые вкладки на
старом сервисе и не понимал, что работает. Поэтому:

```bash
systemctl restart tg-web.service && systemctl is-active tg-web.service
# проверить HTTP 200 на новом пути:
curl -s -o /dev/null -w "%{http_code}\n" -b "auth_token=<TOKEN>" http://127.0.0.1:8080/module/<имя>
```

После перезапуска сказать Фёдору обновить вкладку **Ctrl+F5**
(жёсткое обновление), НЕ простой F5: браузер кэширует HTML страницы,
обычный F5 может отдать старую версию, и Фёдор решит, что сервис не
перезапущен / правка не применилась. Если он говорит «не появилось /
ты не перезапустил» — СНАЧАЛА проверить, что сервер реально отдаёт
новое (`curl` страницы + `grep` нового элемента); сервер отдаёт — значит
это клиентский кэш, а не движок: дать точный URL `/module/<имя>` и
Ctrl+F5, а не перезапускать заново.

**Как ПРАВИЛЬНО проверить «отдаёт ли сервер новое» (грабли самой проверки):**
- Форма модуля — Jinja-шаблон `web/templates/<kind>.html`, рендерится
  `TemplateResponse` в `web/app.py`, а НЕ inline-HTML внутри app.py. Перед
  правкой/брифом подрядчику грепни путь рендера
  (`grep -n "<kind>.html\|TemplateResponse" web/app.py`) и правь ШАБЛОН; пустой
  `git diff web/app.py` — это норма, изменения ищи в `web/templates/`.
- Страница за авторизацией: нужен cookie `auth_token == AUTH_TOKEN` (= env
  `WEB_AUTH_TOKEN`, дефолт `dev`). Запрос БЕЗ куки отдаёт крошечную (~2 КБ)
  страницу входа «Вход — TG Farm» — грепаешь в ней свои новые подписи, не
  находишь и ошибочно решаешь «фичи нет». Всегда `curl -b "auth_token=<TOKEN>" -L`.
- TestClient логинится куком НА КОНСТРУКЦИИ: `TestClient(app,
  cookies={"auth_token": AUTH_TOKEN})`; куки в `.get(cookies=)` новый httpx
  ИГНОРИРУЕТ → снова страница входа (так делает фикстура тестов).
- Жив ли фоновый build — смотреть `systemctl is-active <unit>` / рост лог-файла,
  НЕ `pgrep -f 'claude -p'`: шаблон, который есть и в твоей собственной команде,
  ловит обёртку терминала Hermes → ложное «процесс ещё идёт» (и мнимые «часы»
  работы на самом деле завершённой задачи).

  **ГРАБЛЯ patch по app.py: вставляя новый роут ПЕРЕД существующим, не съешь его
  декоратор.** `@app.get(...)`/`@app.post(...)` и `def` — РАЗНЫЕ строки; если
  old_string кончается строкой-декоратором соседнего роута, а new_string её не
  вернул, декоратор пропадает — функция остаётся без маршрута (роут молча исчезает,
  404/405), а `py_compile` ЗЕЛЁНЫЙ (синтаксис цел). Случалось дважды. После ЛЮБОЙ
  правки роутов: `grep -cE "@app\.(get|post)" web/app.py` до/после ИЛИ `curl` обоих
  путей (нового И соседнего) на 200 — компиляция это не ловит.

### Ретрофит на кит СУЩЕСТВУЮЩЕГО модуля ≠ сборка с нуля (урок 15.10.26)

У старых модулей (create_bots и т.п.) УЖЕ есть контракт: (1) блок
LLM-генерации (`_llm_block.html`, поля `{prefix}_llm_*`), (2) ДОСЛОВНЫЕ
Expert-подписи/плейсхолдеры, закреплённые пачкой parity-тестов
(`test_<kind>_ui_parity.py`, `test_llm_block_macro.py`, `test_llm_gen.py` —

заново на ките» без переноса этих вещей = регрессия: новая страница теряет
LLM-блок и ломает 20+ тестов. Редирект старого пути на новую неполную
страницу роняет весь контракт (23 err+5 fail — поймал полный прогон, НЕ
точечные). Поэтому кит-ретрофит СТАРОГО модуля — отдельный осознанный

включать ТОЛЬКО когда новая страница прошла ВЕСЬ старый контракт. Решение
Фёдора 15.10.26: ретрофит старых — общим проходом в конце, не на ходу.

**КРОСС-МОДУЛЬНЫЕ parity-тесты ломаются от миграции kind, не только свой.**

`new_task.html`. Они НЕ запускаются точечным `pytest tests/test_<k>*.py` — после КАЖДОЙ

test_acc4a_common_blocks.py test_new_task_form_state.py

### Живой спайк (коннект к аккаунту) — СРАЗУ В ФОН, не передний план

Любой запуск, где код ПОДКЛЮЧАЕТСЯ к Telegram живым аккаунтом (спайки
движка) запускать ТОЛЬКО в background=true. На переднем плане 180с-лимит
убьёт процесс на полпути, придётся перезапускать — а это ВТОРОЙ вход в
тот же аккаунт за минуты → предупреждение «ПЕРЕСАЖИВАНИЕ» (норма ≥5 60 мин
между входами), Частые входы Telegram читает как смену устройства и
может отозвать auth_key. Background + notify + timeout 900 с самого начала,
health-check отдельным вызовом через ~20с.
NB: make_client_smart САМ НЕ fail-closed по прокси — если proxy_guard не найдёт
прокси, клиент пойдёт с IP сервера. Перед спайком ВРУЧНУЮ проверять
proxy_guard.check_proxy(sid) по каждому аккаунту, нет прокси — не запускать.

### Включение потоков (thread_pool) в движок модуля — безопасно по-TAO

Перед включением «Управления потоками» у модуля СРАВНИ, как это делают TAO и
Expert, и покажи Фёдору развилку (он требует сравнение конкурентов ПЕРЕД
решением, потом даёт выбор):
- **Expert** — пул на `thread_count` по умолчанию 50, задержка 1/1с: агрессивно,
  анти-детекта почти нет.
- **TAO** (`manager.run_batch`) — `asyncio.Semaphore(concurrency)`, дефолт 3
  (env, клампится 1-32) + `stagger=True`: `human_delay` ПЕРЕД каждым воркером
  (де-коррелированные старты). Консервативно — правильный путь.
- **Наш** `thread_pool.run_pooled` — тот же Semaphore + `wait_from/wait_to`
  (stagger). Включать по-TAO: НИЗКИЙ потолок конкуренции константой в движке
  (напр. `CHANNELS_MAX_CONCURRENCY=5`, `min(thread_count, потолок)` — даже если
  форма прислала 50) + stagger. Тумблер выкл → concurrency=1 (строго
  последовательно, как было), stagger = прежняя пауза между аккаунтами.

**Гонки при параллели чинить ДО включения — мок-тест их НЕ ловит:**
- ОБЩЕЕ порядковое состояние (счётчик имён `name_idx` и т.п.), читаемое ЧЕРЕЗ
  `await`, отдаёт двум воркерам ОДНО значение → дубль (имя канала = палево).
  Лечить атомарным СИНХРОННЫМ счётчиком (`v=self._i; self._i+=1; return v`, БЕЗ
  await внутри — в asyncio вклиниться негде, Lock не нужен); воркер берёт индекс
  ДО сетевого await.
- СТАТИСТИКА (`stats["created"]` и т.п.) при параллели теряет инкременты
  (read-modify-write через await) → у КАЖДОГО воркера свой `stats`, агрегировать
  после `run_pooled`.
- ОБЩИЙ psycopg2-conn НЕ делить между воркерами (не потокобезопасен, курсор
  общий, при interleaving запросы путаются) → DB-зависимое (load_account/
  load_proxy) резолвить ПОСЛЕДОВАТЕЛЬНО ЗАРАНЕЕ одним conn и закрыть, в
  `run_pooled` параллелить ТОЛЬКО сетевую часть (guarded_client + обход).
- Уникальность, которую ГАРАНТИРУЕТ сервер (Telegram username), гонки не боится:
  проигравший ловит `UsernameOccupiedError` и берёт следующий — Lock не городить.
- Сигнатуру рабочей функции (`run_account`) НЕ ломать — прямые parity-тесты
  зовут её со старым набором; общий счётчик давать опциональным `counter=None`
  (None → старое поведение из `stats`).
- Концептуально: параллельные ВСПЛЕСКИ одного действия могут быть ХУЖЕ
  paced-последовательного для анти-детекта — это реальный довод «оставить
  последовательно», озвучивать его Фёдору в развилке, а не включать потоки
  автоматом раз Expert их предлагает.

**Включил фичу — обнови guard-тесты, фиксировавшие «выключено».** Тесты,
кодировавшие СТАРОЕ «потоки отключены/отвергаются»
(`test_disabled_fields_rejected` кейсы, `..._thread_fields_disabled`,
`..._rejects_thread_values`), после одобренного включения КРАСНЕЮТ на полном
прогоне. Это не регрессия — привести их к новому поведению (поля enabled,
значения принимаются и клампятся потолком), НЕ ослаблять молча. Правило общее:
включение ранее-disabled фичи инвалидирует её «это выключено»-сторожа — найти и
обновить их тем же коммитом. Полный прогон обязателен: точечные тесты модуля эти
сторожа не трогают.

### Включение потоков (thread_pool) в движок модуля — безопасно по-TAO (обкатано 4/5/6)

Перед включением «Управления потоками» СРАВНИ TAO и Expert и покажи Фёдору
развилку (он требует сравнение конкурентов ПЕРЕД решением): Expert — пул 50,
задержка 1/1с (агрессивно); TAO `manager.run_batch` — `Semaphore(3)` + stagger
(`human_delay` перед воркером) — консервативно, НАШ путь. Включать через
`thread_pool.run_pooled(items, worker, concurrency, wait_from, wait_to,
return_exceptions=True)` с НИЗКИМ потолком-константой в движке
(`<MODULE>_MAX_CONCURRENCY=5`, `min(thread_count, потолок)` — даже если форма
прислала 50) + stagger. Тумблер выкл → concurrency=1 (строго последовательно).

ГОНКИ чинить ДО включения (мок-тест их НЕ ловит, только живой/interleaving-тест):
- Общий порядковый счётчик (name_idx), читаемый через await → двум воркерам одно
  значение → дубль имени=палево. Лечить СИНХРОННЫМ атомарным счётчиком
  (`v=self._i; self._i+=1; return v`, без await — в asyncio вклиниться негде,
  Lock не нужен), индекс брать ДО сетевого await.
- Статистика (`stats[x]+=1` через await) теряет инкременты → у КАЖДОГО воркера
  свой stats, агрегировать после run_pooled.
- Общий psycopg2-conn НЕ делить: DB-резолв (load_account/load_proxy) делать
  ПОСЛЕДОВАТЕЛЬНО заранее одним conn и закрыть, параллелить только сеть.
- Серверная уникальность (Telegram username) гонки не боится — проигравший ловит
  Occupied, берёт следующий; Lock не городить.
- Сигнатуру рабочей функции НЕ ломать — прямые parity-тесты зовут её по-старому;
  общий счётчик давать опционально `counter=None` (None → старое поведение).
- Параллельные ВСПЛЕСКИ одного действия могут быть ХУЖЕ paced-последовательного
  для анти-детекта — это реальный довод «оставить последовательно», озвучить.

ВКЛЮЧИЛ ФИЧУ — ОБНОВИ guard-тесты, фиксировавшие «выключено»
(`test_disabled_fields_rejected` кейсы, `..._thread_fields_disabled`,
`..._rejects_thread_values`): после одобренного включения они КРАСНЕЮТ на полном
прогоне (НЕ на точечных). Привести к новому поведению (поля enabled, значения
принимаются и клампятся), снять `_reject_disabled_fields` по thread-полям,
`threads_block(enabled=true)`, убрать `disabled` с полей. Это не ослабление — тем
же коммитом. ГРАБЛЯ расширения интерфейса: движок начал звать
`client.delete_dialog(entity, revoke=...)` → ручные мок-клиенты с
`delete_dialog(self, entity)` падают на чужом шарде — грепнуть моки и дописать kwarg.

**ПАРАЛЛЕЛЬ ДЛЯ destructive/leave-операций — по АККАУНТАМ, НЕ по диалогам.**
Препнутый агентом ops-модуль (unsubscribe_ops, delete_dialogs_ops) часто паралелит
на уровне ДИАЛОГОВ одного аккаунта (Semaphore вокруг leave/delete). Для
анти-детекта это ХУЖЕ последовательного: залп одинаковых LeaveChannel/delete с
ОДНОГО аккаунта за секунды = явный паттерн бота → спам-блок. Правило: пул
(`run_pooled`) ставить по АККАУНТАМ (каждый свой lease/клиент/finally, cap=5 +
stagger), а внутри аккаунта диалоги обходить ПОСЛЕДОВАТЕЛЬНО с паузами из профиля.
Про-дайловую конкуренцию из ops не включать.

**skip_admin на leave — необратимость, гейтить обязательно.** Выход из канала/
группы, где аккаунт admin/owner, НЕОБРАТИМ и теряет права. Любой unsubscribe/leave
с массовым охватом обязан иметь опцию `skip_admin` (через `is_admin` →
GetParticipant perms) и пропускать такие чаты; не удалось проверить права — НЕ
блокировать отписку (fallback), но саму опцию давать.

**Интеграция prepped ops-модуля = ПРОВОД, не переписывание.** Движок уже есть и
покрыт тестами — новую способность подключать ЧЕРЕЗ готовый `*_ops.py`
(локальный импорт внутри функции движка), не копируя telethon-вызовы в третий раз.
Любой `# TODO verify API` в коде агента ЗАКРЫТЬ по РЕАЛЬНОЙ версии либы до
доверия (telethon 1.45.0: `contacts.BlockRequest(id=entity)` валиден, `client.block_user`
НЕТ — alias только в ≥1.26; fallback через raw-функцию). Проверка — `.venv/bin/python
-c "import telethon; from telethon.tl.functions... import X"`, не по памяти.

**Снятие ЧЕСТНОГО ОТКАЗА при включении фичи — обновить и refuse-тесты.** Кроме
`_reject_disabled_fields`-сторожей, у runner бывают явные `build_command ... raises
ValueError` отказы («движок не умеет X») со своими тестами `test_build_command_<kind>_<feat>_refuses`.
Убрал отказ (движок научился) → эти тесты КРАСНЕЮТ: переписать `_refuses` →
`_passes` (ждать, что флаг/`--threads` реально в cmd), тем же коммитом.

### Живой автоответчик = ПОВЕДЕНИЕ человека, не только текст (урок live-теста)

Движок-слушатель, отвечающий на входящие ЛС (`answering_machine_smart`,
`chat_responder`), по умолчанию выдаёт РОБОТНЫЙ паттерн, который владелец
видит сразу. Обязательные элементы человечности (мок их НЕ ловит — всплывают
ТОЛЬКО на живой переписке):
- **Пометить входящее прочитанным — НО НЕ МГНОВЕННО.** `await
  client.send_read_acknowledge(chat_id, max_id=event.id)` нужен (иначе у
  собеседника нет «прочитано»/двойной галки, аккаунт выглядит мёртвым), НО
  ставить его в момент прихода = «прочитано» прилетает в ту же секунду = палево
  (владелец замечает сразу). Помечать прочитанным в ВОРКЕРЕ после человеческой
  паузы «пока заметил и открыл» (напр. `sleep(uniform(4,20))` поверх окна
  дебаунса), а не в хендлере NewMessage. Порядок живого человека: пришло →
  пауза-замечание → прочитал → «печатает…» → ответил.
- **Показывать «печатает…» на время раздумья:** `async with client.action(chat_id,
  "typing"): await sleep(delay); <отправка>` — индикатор гаснет сам после отправки.
- **ДЕБАУНС пачки сообщений:** человек пишет одну мысль в 3 сообщения подряд;
  ответ НА КАЖДЫЙ обрывок отдельным сообщением = явный бот. Копить входящие за
  окно тишины (5-15с) и отвечать ОДНИМ ответом на всё.
- **ПАМЯТЬ диалога:** без состояния движок здоровается в КАЖДОМ ответе («Привет!»
  на 5-е сообщение подряд). Держать историю переписки per-chat и передавать в
  промпт, чтобы не представляться заново.
- **«Отвечать каждому один раз» — ОПЦИЯ (флаг), не зашитый дедуп.** Хардкод
  `replied`-set глотает все follow-up сообщения собеседника (ответил раз —
  дальше молчит, оператор думает «сломалось»). Вынести в флаг (`--answer-once`),
  гейтить И проверку, И запись в set; дефолт — отвечать на каждое. Runner маппит
  опцию формы в ЭТОТ флаг, а НЕ в `--once` (у движка `--once` = разовый ~5-сек
  прогон проверки настроек, совсем другое — спутать легко по имени).
- Перезапуск слушателя ради подхвата правки = ещё ОДИН connect к живому
  аккаунту (stop→пауза→start). Не гонять правка-за-правкой на боевом — добивать
  логику юнит-тестами, живьём проверять итог один раз (см. бюджет живых входов).

### Автоответчик = ЛИЧНОСТЬ: психопрофиль на аккаунт в БД

Масштаб автоответчиков = каждый аккаунт — ОТДЕЛЬНАЯ личность, хранимая в БД
(`personas.py`, таблица `account_personas`, PK=session_id). Правила (решения Фёдора):
- **«Эпоксидка»: удаления НЕТ.** Добавить/править можно (`upsert_persona`), delete-функции
  быть не должно (сторож `test_no_delete_function`: `not hasattr(personas,'delete_*')`).
- **Основные поля структурированно + ОДНО большое свободное поле** `profile_text`
  («всё остальное»: психопрофиль/табу/примеры фраз) — по требованию Фёдора.
- **ЯЗЫК ОТВЕТА** (`reply_language`): аккаунт понимает ЛЮБОЙ язык собеседника, но
  ВСЕГДА отвечает на своём (пишут по-русски → украинский аккаунт отвечает по-украински).
  Это жёсткое правило в конце системного промпта.
- **Билдер промпта детерминированный** (`build_system_prompt` собирает промпт из полей
  без LLM — надёжно), LLM используется ОТДЕЛЬНО для ГЕНЕРАЦИИ `profile_text` по
  короткому брифу (переключатель вручную/LLM). Кэш готового промпта — `system_prompt`.
- **Привязка к движку:** `answering_machine_smart.run_session` в начале делает
  `task = personas.resolve_prompt(sid, fallback=task) or task` — есть личность →
  её промпт, нет → переданная CLI-задача. Каждый аккаунт отвечает своим характером.
- Чистые функции (билдер + resolve) тестить без БД через monkeypatch `get_persona`.

### send_by_id (цель = числовой user_id) — нужен access_hash через ЧАТ-ДОНОР

Отправка по ГОЛОМУ `user_id` незнакомцу падает `Could not find the input entity
for PeerUser` — это НЕ баг модуля, а устройство MTProto: пользователь адресуется
парой `InputPeerUser(user_id, access_hash)`, а `access_hash` сервер выдаёт только
аккаунту, который юзера «видел». Telethon кэширует пары `(id, access_hash)` в
SQLite-таблице `entities` внутри `.session`; кэш наполняется из: участников общей
группы/канала (`GetParticipants`), входящего сообщения, `GetDialogs`, контактов
(ImportContacts), resolve @username. Авторитетно подтверждает саппорт Telegram
Expert (БЗ, source=telegram): «в ТГ нет взаимодействия по айди без ЧАТА-ДОНОРА
(откуда id собраны); просто список id без донора ничего не даёт». Отсюда правильный
`send_by_id`: принимать id ТОЛЬКО в связке с access_hash (из нашего парсера,
идея #20 — хранить `(user_id, access_hash, источник)`) ИЛИ с донор-чатом, в который
аккаунт-отправитель заходит и парсит участников:
```python
await client.get_participants(donor_chat)      # Telethon кэширует access_hash всех
peer = await client.get_input_entity(user_id)  # теперь берётся из кэша сессии
await client.send_message(peer, text)           # id не среди участников → пропустить
```
access_hash НЕ ПЕРЕНОСИМ между аккаунтами/авторизациями (docs.telethon +
core.telegram дословно): собрать одним аккаунтом и слать другим НЕЛЬЗЯ — резолвить
и слать должен ОДИН аккаунт. ЗАКРЫТЫЕ УЧАСТНИКИ (`ChatAdminRequiredError`) — не тупик:
вторым проходом `iter_messages(donor)` по отправителям; кого `get_input_entity`
не взял (min) — `InputPeerUserFromMessage(peer=donor, msg_id=msg.id, user_id=sid)`
(юзер, засветившийся в сообщении, достижим БЕЗ полного хэша). `aggressive=True`
в Telethon 1.45 мёртв. Юзер без @username, без номера-в-контактах И не мелькнувший
в доноре — недостижим (предел протокола + слова Expert). Живой smoke по номерам:
телефон резолвится лишь при приватности «кто может найти по номеру = все» — иначе
`номер не найден в Telegram` (модуль цел). ПОЛНЫЙ рецепт (два прохода + min + схема
хранения + код) — `references/send-by-id-resolve-access-hash.md`.

### time_window.py — core-блок «за последние N часов» (переиспользуемый)
